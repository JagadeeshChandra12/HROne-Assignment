# DECISIONS.md

1. **Indexes.** `employees`: a unique index on `emp_code` (enforces the identity rule without a check-then-insert race) and a plain index on `department` (headcount/department queries). `attendance_logs`: a unique compound index on `(emp_code, date)` — it is both the duplicate-punch-in guard and the natural key lookup used by punch-out, regularize and the per-employee analytics; a compound `(date desc, emp_code asc)` index for the default attendance listing and date-range-only analytics (department summary/leaderboard without a department filter); and `(emp_code, punch_in desc)` to find "the most recent record" during punch-out. I considered a separate single-field `date` index but the compound `(date, emp_code)` index already covers that prefix, so I dropped it to keep the index set small.

2. **Punch-in race.** Both requests pass employee validation and build an identical document, then both call `insert_one`. The unique index on `(emp_code, date)` lets MongoDB itself pick a winner: the first insert succeeds (201), the second raises `DuplicateKeyError`, which I catch and turn into 409. There is no read-then-write window — the database, not application logic, is the single source of truth for uniqueness.

3. **Ties.** Ranking is computed in Python after grouping in Mongo: employees are sorted by `(-total_late_minutes, emp_code)`, and a row's rank is the 1-based position of the *first* row with that total (competition ranking — ties repeat a rank and the next distinct value skips ahead). Rows are then kept while `rank <= limit`, so a 5-way tie sitting at the cutoff all get returned even though that makes the response longer than `limit`.

4. **Headcount.** The department summary first aggregates `employees` alone (`joined_on <= month end`, grouped by department) to get headcount — this does not touch `attendance_logs` at all, so employees with zero logs are counted. A second aggregation over `attendance_logs` (filtered to that department's `emp_code`s) supplies present/late/leave numbers, merged onto the same department keys in Python; a department with headcount but no logs simply keeps its zero defaults.

5. **At 100x the data,** I'd stop computing department summary in two round trips from the API process and instead maintain daily/monthly rollup documents (written incrementally at punch-in/out/regularize time), so analytics reads hit a small pre-aggregated collection instead of scanning `attendance_logs` every call.
