# REVIEW.md

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health()` | Always returns `{"status":"ok"}` without ever touching MongoDB. If the database is down, the readiness probe still reports healthy. | Stop MongoDB, call `GET /health` -> still 200. | Call `db.command("ping")` inside a try/except; return 503 on any exception. |
| 2 | `compute_late_minutes` | Truncates to minutes (`int(seconds/60)`) *before* comparing to the 10-minute grace period, and the comparison + conversion never considers IST at all (it uses whatever naive local time `punch_in` happens to be in). | Shift 09:30, punch-in at 09:40:01 (601s late): `int(601/60)=10`, `10>10` is False -> returns 0 instead of the required 10 (see R2's own worked example). On a server not running in IST, every punch is misjudged. | Convert the punch instant to IST explicitly (`punch_in_utc + 5:30`), compare `total_seconds() > 600`, and only then floor-divide by 60. |
| 3 | `compute_work_hours` | Uses Python's built-in `round()`, which is round-half-to-even ("banker's rounding"), not the required round-half-up. | `round(2.005, 2)` style inputs land on the wrong side of `.xx5` boundaries; e.g. a duration whose seconds/3600 is exactly `x.125` rounds down instead of up. | Added `round_half_up()` using `decimal.Decimal(...).quantize(..., ROUND_HALF_UP)` and used it everywhere R4/R8 apply. |
| 4 | `compute_overtime` | Builds `end` as a *timezone-aware* IST datetime but subtracts it from `punch_out`, which is naive (local system time) — mixing aware/naive datetimes raises `TypeError` at runtime. It also never enforces the "only counts if >= 30 minutes" rule, and never accounts for an overnight shift's end falling on the next calendar day. | Call punch-out for any record where `shift_end` logic executes -> crashes with `TypeError: can't subtract offset-naive and offset-aware datetimes`. Even patched, 5 minutes of overtime would be reported instead of 0. | Rewrote as `compute_overtime_minutes` using a single naive "IST" frame throughout, with the end instant moved to the next day for overnight shifts, and a `>= 30` floor check. |
| 5 | `EmployeeIn` | No field constraints at all: no `emp_code` pattern, no email format, no `HH:MM` pattern on shifts, no real-date check on `joined_on`, and `shift_start == shift_end` is accepted. | `POST /employees` with `emp_code: "x"`, `email: "not-an-email"`, `shift_start == shift_end` all return 201 instead of 422. | Added `Field(pattern=...)`/length constraints matching `openapi.yaml`, a `joined_on` calendar-date validator, and a model validator rejecting `shift_start == shift_end`. |
| 6 | `create_employee` | Check-then-insert (`find_one` then `insert_one`) with **no unique index** anywhere in the starter. Two concurrent creates with the same `emp_code` both pass the check and both insert. | Fire two parallel `POST /employees` with the same `emp_code` -> both succeed, collection ends up with two documents sharing one `emp_code`. | Created a unique index on `employees.emp_code` at startup and now rely on catching `DuplicateKeyError` for the 409, with no pre-check. |
| 7 | `create_employee` | `created_at = datetime.now()` (naive local time) is returned straight from `model_dump()`/Mongo as a Python `datetime`. FastAPI's default encoder serializes that as an ISO-8601 string, not the required integer epoch milliseconds, and it isn't even UTC. | Response body has `"created_at": "2026-01-05T04:30:00"` instead of an integer; on a server not in UTC the value is simply wrong. | Store `created_at` as a UTC `datetime` and convert explicitly to epoch ms (`dt_to_ms`) in every response. |
| 8 | `list_employees` | `skip = page * page_size` — page 1 already skips `page_size` documents, so the *first* page is missing and every page shows the next page's data. | `GET /employees?page=1&page_size=2` with 6 employees returns employees 3-4, not 1-2. | `skip = (page - 1) * page_size`. |
| 9 | `list_employees` | `total = db.employees.count_documents({})` ignores the `department` filter — `total` always reflects the whole collection, not the filtered set, violating R10. | `GET /employees?department=Sales` with 2 Sales employees out of 6 total returns `"total": 6`. | Count with the same `filt` used for the query. |
| 10 | `list_employees` | No `.sort()` at all — results come back in whatever order Mongo's storage happens to return them, not ascending `emp_code` as required. | Insert employees out of code order, list them, order is unspecified/insertion order. | Added `.sort("emp_code", 1)`. |
| 11 | `list_employees` / `list_attendance` | `page`/`page_size` are plain `int` parameters with no bounds — a client can send `page_size=100000` or `page=-5`, defeating pagination and R10's stated max of 100. | `GET /employees?page_size=100000` -> 200, dumps everything; `page=0` -> negative skip, undefined behaviour. | Replaced with `Query(..., ge=1)` / `Query(..., ge=1, le=100)`, which FastAPI turns into a 422. |
| 12 | `punch_in` | `emp = db.employees.find_one(...)` result is never checked for `None` before `emp["shift_start"]` is read. | `POST /attendance/punch-in` with an unknown `emp_code` -> `TypeError: 'NoneType' object is not subscriptable` -> unhandled 500, instead of the required 404. | Added an explicit `if not emp: raise HTTPException(404, ...)` before any field access. |
| 13 | `punch_in` | `ts = datetime.fromtimestamp(...)` / `datetime.now()` are naive, server-local-time values; the attendance `date` is derived from local time, not IST (R1), there is no overnight-shift handling, no truncation to whole seconds, and `punched_at` is never validated as a proper epoch-millisecond value (a seconds-looking int, a float, or a string would all be silently accepted and misinterpreted). `status` also accepts any string, not just `PRESENT`/`WFH`/`ON_DUTY`. | Deploy the service on a UTC host and punch in at 09:35 IST -> the record lands on the wrong calendar date and `late_minutes` is computed against the wrong wall-clock time; `punched_at: 1700000000` (seconds, not ms) is accepted without error. | Added a strict, range-checked `EpochMillis` type, an IST-aware `attendance_date_for_punch_in()` helper with overnight-shift logic, truncation to whole seconds in `ms_to_dt`, and a `Literal["PRESENT","WFH","ON_DUTY"]` status field. |
| 14 | `punch_in` | Check-then-insert (`find_one` then `insert_one`) for the "already punched in" check, and there is no unique index on `(emp_code, date)` anywhere. | Fire two parallel punch-ins for the same employee at the same instant -> both succeed, two documents exist for the same `(emp_code, date)`. | Added a unique index on `attendance_logs.(emp_code, date)` and now rely on catching `DuplicateKeyError` for the 409 instead of a pre-check. |
| 15 | `punch_in` / `list_attendance` | Both responses add an `"id": str(_id)` field. Attendance records have no id in the contract at all (`_id` must never leak, under any field name). | Inspect any `POST /attendance/punch-in` or `GET /attendance` response body -> contains an unexpected `id` field. | Removed; records are serialized through `serialize_attendance()`, which only emits contract fields. |
| 16 | `list_attendance` | `docs = list(db.attendance_logs.find(q))` loads **every matching document into Python** and then sorts and slices it in-process for pagination — explicitly called out as unacceptable at ~100k documents. | On a large collection this endpoint's latency and memory grow with the size of the filtered result, not with `page_size`. | Pushed sort/skip/limit into the Mongo query (`.sort(...).skip(...).limit(...)`) backed by an index, and compute `total` via `count_documents` on the same filter. |
| 17 | `list_attendance` | `date_from`/`date_to` are compared nowhere; an inverted range (`date_from > date_to`) silently returns an empty page instead of the required 422. `status` also accepts any string. | `GET /attendance?date_from=2026-07-10&date_to=2026-07-01` -> 200 with `"items": []` instead of 422. | `build_attendance_filter()` now raises 422 when `date_from > date_to`; `status` is typed as a `Literal` of the five valid values. |
| 18 | Whole file | No indexes are created anywhere, despite the environment contract requiring "create all indexes at startup, idempotently." This is the root cause behind items 6 and 14 (uniqueness) and behind every analytics/list endpoint being unable to avoid a collection scan. | `db.attendance_logs.index_information()` on a fresh database shows only the default `_id` index. | Added a `create_indexes()` call wired into FastAPI's `lifespan`, creating the unique `(emp_code,date)` and `emp_code` indexes plus the two supporting indexes described in `DECISIONS.md`. |

## Examined and judged not a defect
- **`load_dotenv()` default behaviour.** It does not override variables already present in `os.environ`, which already satisfies "real environment variables must win" — no change needed.
- **Using PyMongo's synchronous driver inside `def` (not `async def`) endpoints.** FastAPI runs sync endpoints in a thread pool, so blocking Mongo calls do not block the event loop; this is a reasonable, simple choice for this assignment's scale and was kept.
- **Missing endpoints** (`punch-out`, `regularize`, the four analytics endpoints, `/admin/explain/...`). These are TODO stubs in the starter, not defects in existing logic — they are implemented fresh as Part B/C of this assignment.
